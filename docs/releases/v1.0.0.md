# v1.0.0 — Forecasting, recovery and appliance-aware charging

Released: 2026-10-22

This first major release rolls up the work since v0.3.0: 92 non-merge commits
across forecasting, measurement quality, automation, monitoring and the dashboard.
It is a substantial product milestone, not a guarantee of forecast accuracy or
uninterrupted electrical service.

## Highlights

### Appliance-aware grid charging

- Connect LG ThinQ with a read-only token saved encrypted on the server.
- Explicitly map any supported LG appliance to the Jackery whose 220/240 V
  output it actually uses. Device type never implies wiring or voltage.
- Fresh active states stop grid charging; this includes the dryer's observed
  powered-on `INITIAL` state, not only a running cycle. Manual reservations
  remain effective when LG monitoring is unavailable.
- Use valid remaining-time estimates in charging plans and estimated SOC at
  finish. Recheck state and recalculate when reports change; timers alone do
  not release an active-state hold.
- Refresh all discovered appliances, not just mapped ones. Only mapped
  appliances control that Jackery's charging plug.
- Surface monitoring problems with a persistent Automation warning and a
  separate red dot visible from other dashboard tabs. Clear both on recovery.

### More trustworthy forecasts and accuracy reporting

- Preserve the original sunset-to-sunrise forecast separately from rolling
  updates, so late revisions cannot make overnight accuracy look better.
- Learn drain corrections from validated multi-night, SOC-range-specific
  discharge evidence, with coverage, freshness and discontinuity checks.
- Retain validated calibration across sparse SOC bins using a bounded pooled
  fallback; follow sustained household-load changes without learning brief spikes.
- Respect already measured SOC when applying charge ceilings and account for
  curtailment during diversion lookahead. Align hourly weather and partial hours.
- Persist weather forecasts and expose last-good/fallback weather context when
  the weather service is unavailable. Forecasts remain estimates, not promises.

### Stale-data recovery and historical repair

- Detect repeated frozen discharge measurements even when HTTP responses arrive.
- Reconnect with bounded backoff and preserve detection evidence across restarts.
- Exclude suspect main/pack readings from new samples, SOC rules, forecasts and
  charging decisions instead of treating receipt time as proof of freshness.
- Archive confirmed affected history reversibly, protect against late writes and
  derived-data backfills, and validate selective restoration against overlapping
  incidents. Missing energy and sunrise actuals remain unknown, not zero.

### Automation, devices and the dashboard

- Tighten smart-charge SOC/capacity freshness checks, include final-hour top-ups,
  save exact decision inputs and correctly refresh conflicting-rule switches.
- Improve excess diversion with reserve guards, overload/no-load handling,
  pack-balance windows, emeter or learned-load accounting and recovery state sync.
- Make AC auto recovery configurable per device and honor manual AC-off actions;
  add rescue/watchdog recovery and reported hardware-trip handling.
- Add Explorer 1000 v2 catalog support and explicit read-only Jackery Home EU
  discovery. Add pack temperature/history and firmware-availability indicators.
- Support Anthropic or OpenAI for user-initiated advisor reviews, with richer
  decision, control and pack-history evidence. Suggested changes need approval.
- Redesign Energy reporting with daily breakdowns, records, search and CSV;
  reduce redundant requests and historical scans without slowing live telemetry.
- Fix cached-shell startup, stale responses after device switches, HTML-injection
  paths and secret handling. Support optional Cloudflare Access Google sign-in
  while retaining the app's authenticated LAN fallback.

## Important behavior and limitations

**LG monitoring failures are non-blocking by explicit policy.** Missing/expired
tokens, API/network errors and unknown/stale/missing appliance states show a
warning but do not hold grid charging OFF. These states remain unknown, not
measured OFF. A fresh LG disconnected response is instead labelled assumed OFF.
A Wi-Fi or monitoring outage can therefore allow charging while an appliance is
running. Use **Reserve 240 V availability (manual hold)** when that availability
is required. This cloud-based software guard is not a hardware safety interlock
and does not react instantaneously.

Jackery Home EU support remains read-only and hardware validation is pending.
Portable controls, automation and energy integration are disabled for Home
systems. Firmware indicators do not install firmware. Measurements, supported
cloud APIs and forecasts depend on upstream devices/services; no accuracy claim
or protection guarantee is implied by the version number.

## Upgrade

1. Use an online SQLite backup and preserve the existing `/data` volume and its
   encryption key. Do not delete or replace that key; existing secrets need it.
2. Review per-device automation, Kasa plug mappings, recovery settings and the
   LG policy above. LG is opt-in; do not assume appliances are wired correctly
   just because they appear in discovery.
3. For a pinned deployment, set **both** monitor and bridge image references to
   `ghcr.io/yaniverel-code/jackery-monitor:v1.0.0`, then pull and recreate using
   your existing Compose project. There is a brief telemetry interruption.
4. Confirm live main/pack readings, the desired charging-plug state and Automation
   warnings after startup. Refresh an old dashboard/PWA if its shell is cached.
5. Historical correction is not a license to delete flat SOC intervals blindly.
   Preserve evidence and use the guarded archive/restore tools only after review.

## Validation and artifacts

The application baseline passes **954 Python tests and 42 dashboard tests**.
CI covers Python 3.11/3.12, lint and cloud/bridge smoke tests. Tracked-source secret
scanning and desktop/mobile warning/recovery checks passed. Production checks
verified fresh readings, authenticated endpoints, the new UI assets and unchanged
charging settings; failure-policy checks ran in an isolated process without
injecting faults into the live controller.

Versioned images are built from the release tag. The build publishes SBOM and
maximum-detail provenance attestations alongside the image. Release attachments
include that build evidence and checksums; they do not contain runtime data or
credentials and are not a signed security certification.

Blanket registry cleanup is removed so published image pins and their linked
attestations are not deleted by newer builds. Registry storage can grow until
a release-aware retention policy is implemented.
